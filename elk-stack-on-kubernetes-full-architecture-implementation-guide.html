3. Secrets — Vault → External Secrets → Kubernetes

Why no hardcoded passwords

Every password lives exclusively in HashiCorp Vault. The External Secrets Operator (ESO) reads the Vault secret path and writes a Kubernetes Secret object. No password ever appears in any YAML file or container environment definition in plain text.

ExternalSecret manifest (externalsecret.yaml)

secretStoreRef: vault-secretstore        # pre-existing SecretStore pointing at Vault
target.name:    elasticsearch-credentials  # the K8s Secret this creates
data:
  secretKey: password
  remoteRef:
    key:      elastisearch                 # Vault path
    property: kibana-token                 # field inside the Vault secret

The resulting secret elasticsearch-credentials has a single key password. Every component that needs the Elasticsearch password reads it from this secret via secretKeyRef. ESO refreshes it every hour.

Startup dependency chain

1
ESO syncs elasticsearch-credentials from Vault into the namespace.
2
Elasticsearch StatefulSet starts; the ELASTIC_PASSWORD env var is injected from the secret.
3
The password-sync sidecar waits for ES health, then forcibly sets the elastic user password to match the secret — ensuring no drift after PVC restores.
4
The sidecar registers the k8s-single-node index template (priority 200, number_of_replicas: 0) and patches any existing k8s-* indices to replicas=0.
5
create-kibana-token Job: initContainer waits for the secret → second initContainer waits for ES security API → main container runs manage-es-token.js create.
6
The Node.js script calls POST /_security/service/elastic/kibana/credential/token/kibana-token on ES and writes the returned token into the secret kibana-es-serviceaccount-token.
7
Kibana Deployment starts and reads ELASTICSEARCH_SERVICEACCOUNTTOKEN from that secret — no login screen, no manual token copy.
8
kibana-setup Job runs setup.sh: deletes stale data views, creates k8s-logs-* / k8s-error-* / k8s-misc-* data views, a dashboard, and two saved searches via the Kibana Saved Objects API.

4. Component Deep-Dive

4.1 Filebeat (DaemonSet)

Image: docker.elastic.co/beats/filebeat:8.10.2 — kept at 8.x because Filebeat 9 has breaking changes to the add_kubernetes_metadata processor.

The log path problem on k3s

k3s uses the Docker JSON log driver. The actual log data lives at:

/var/lib/docker/containers/<id>/<id>-json.log

But container runtimes expose two layers of symlinks on top:

/var/log/containers/<name>.log
    → /var/log/pods/<namespace>_<pod>/<container>/0.log
        → /var/lib/docker/containers/<id>/<id>-json.log

Filebeat's type: container input follows this double-symlink chain automatically, but only if all three directories are mounted into the DaemonSet pod.

Volume mounts required

Host pathPurpose
/var/log/containersTop-level symlinks — Filebeat reads the directory listing
/var/log/podsMiddle symlinks — first hop in the chain
/var/lib/docker/containersActual JSON log files — must be mounted for Filebeat to open them
/var/lib/filebeat-data (hostPath)Registry — stores per-file read offsets so logs are not reshipped after pod restart

RBAC

The filebeat ClusterRole grants get/list/watch on pods, nodes, namespaces, replicasets, and jobs. This is required by the add_kubernetes_metadata processor to enrich every log line with pod labels, namespace, and node name.

Config highlights

filebeat.inputs:
  - type: container
    paths: ["/var/log/containers/*.log"]
    stream: all
    tags: ["kubernetes", "container-logs"]

processors:
  - add_kubernetes_metadata:
      host: ${NODE_NAME}          # injected via fieldRef: spec.nodeName
      matchers:
        - logs_path:
            logs_path: "/var/log/containers/"
  - drop_fields:
      fields: ["agent", "ecs", "input"]
  - add_fields:
      fields: { cluster: "k8s-prod" }

output.logstash:
  hosts: ["logstash.observability.svc.cluster.local:5044"]

4.2 Logstash (Deployment)

Image: elastic/logstash:9.1.7

Single-replica Deployment. Receives Beats events on port 5044 (Lumberjack protocol). The pipeline has three stages: input → filter → output.

Filter pipeline — what happens to each log event

1
Kubernetes metadata promotion — flattens [kubernetes][namespace], [kubernetes][pod][name] etc. into top-level fields k8s_namespace, k8s_pod, k8s_container, k8s_node so they are searchable in Kibana without nested field syntax.
2
JSON parsing — if message starts with {, parse it into a structured sub-object and promote level/severity into log_level.
3
Log level normalisation — cascades through log_level → [log][level] → [level] → defaults to "info". Always lowercased.
4
Timestamp override — if the structured payload has its own @timestamp, use it instead of Logstash's ingestion time.
5
kube-system / kube-public drop — internal cluster infrastructure logs are dropped entirely; they are noise in Kibana.
6
Field cleanup — removes agent, ecs, input, log, host, beat, tags to reduce index size.

Output routing

ConditionIndex patternExample
log_level is error / fatal / criticalk8s-error-YYYY.MM.ddk8s-error-2026.07.25
event has a k8s_namespacek8s-logs-{namespace}-YYYY.MM.ddk8s-logs-argocd-2026.07.25
everything elsek8s-misc-YYYY.MM.ddk8s-misc-2026.07.25
⚠ Why index names do NOT start with logs-
Elasticsearch 9 ships a built-in index template named logs at priority 100 that matches the glob logs-*-*. Any matching index is automatically converted into a data stream, which enforces number_of_replicas: 1 (yellow on a single-node cluster) and rejects plain index write operations with HTTP 400. Renaming to k8s-* avoids this entirely.

4.3 Elasticsearch (StatefulSet)

Image: elastic/elasticsearch:9.1.7 · Storage: 10 Gi PVC · Memory: request 1600 Mi / limit 2 Gi

Key environment variables

VariableValueWhy
discovery.typesingle-nodeSkips zen discovery; starts immediately without quorum.
xpack.security.http.ssl.enabledfalseES 9 auto-enables TLS on first start. Disabled so all in-cluster traffic stays plain HTTP and no certificate management is needed.
xpack.security.transport.ssl.enabledfalseSame reason — transport layer between nodes (only one here) is plain text.
ELASTIC_PASSWORDfrom elasticsearch-credentials secretSets the built-in elastic superuser password at first boot.

Password-sync + index-template sidecar

A curlimages/curl:8.7.1 sidecar runs in the same pod and does four things on every pod start:

1
Polls GET /_cluster/health until ES responds — ensures the main container is ready before taking action.
2
Password sync — calls PUT /_security/user/elastic/_password with the value from the K8s secret. If the password already matches, ES returns 200. If a PVC was restored and the password drifted, this resets it. Handles 401 as a fallback.
3
Index template registration — PUT /_index_template/k8s-single-node with index_patterns: ["k8s-*"], priority: 200, number_of_replicas: 0. Priority 200 beats the built-in logs template (100) and Logstash's own template (1). All future k8s-* indices are created green.
4
Patch existing indices — PUT /k8s-*/_settings { "number_of_replicas": 0 } brings any already-created indices from yellow to green without requiring a delete/recreate.

After step 4 the sidecar calls exec sleep infinity so it never restarts (a restarting sidecar in a running pod would be disruptive).

4.4 Kibana Token Automation (pre-install-job)

This is the core of the "zero manual steps" requirement. Kibana 8+ uses an Elasticsearch service account token rather than a username/password to authenticate to ES. Generating this token used to require a manual elasticsearch-service-tokens create command. The following automation eliminates that entirely.

create-kibana-token Job

ContainerRole
initContainer: wait-for-credentialsPolls until kubectl get secret elasticsearch-credentials -o jsonpath='{.data.password}' returns a non-empty value. This waits for ESO to finish syncing from Vault.
initContainer: wait-for-elasticsearchFirst checks TCP port 9200 with nc -z, then polls GET /_security/user/elastic with the password. This ensures ES is fully initialised, not just accepting TCP connections.
container: create-tokenRuns node /helm-scripts/manage-es-token.js create. The script deletes any existing token (idempotent), calls POST /_security/service/elastic/kibana/credential/token/kibana-token, and writes the returned token value into the K8s secret kibana-es-serviceaccount-token.

manage-es-token.js — what the script does

// create mode:
DELETE /_security/service/elastic/kibana/credential/token/kibana-token  // idempotent
POST   /_security/service/elastic/kibana/credential/token/kibana-token  // get new token
→ write token.value into K8s Secret "kibana-es-serviceaccount-token" key "password"

// clean mode (post-delete Helm hook):
DELETE /_security/service/elastic/kibana/credential/token/kibana-token
DELETE K8s Secret "kibana-es-serviceaccount-token"

The script uses the in-cluster service account token (/run/secrets/kubernetes.io/serviceaccount/token) and the cluster CA to authenticate against the K8s API — no kubeconfig needed.

RBAC for the token job

The kibana-token-sa ServiceAccount is granted a Role with get / create / patch / delete on secrets in the observability namespace only — least-privilege.

4.6 Kibana Setup Job (kibana-setup-job)

After Kibana starts, a second Job runs setup.sh via curlimages/curl to provision all Kibana objects automatically.

What setup.sh does

0
Delete stale data views — removes logs-k8s-star, logs-error-star, logs-misc-star if they exist (404-safe). These were the old names before the index rename.
1
Data view: k8s-logs-* — default data view, time field @timestamp. Covers all per-namespace indices.
2
Data view: k8s-error-* — dedicated view for error/fatal/critical events only.
3
Data view: k8s-misc-* — catch-all for logs without a namespace.
4
Set default data view — calls the /api/saved_objects/config/9.1.7 uiSettings API to set k8s-logs-star as the default, so Discover opens immediately on the right data.
5
Dashboard: Kubernetes Logs Overview — pre-built histogram visualisation of log events by namespace over time.
6
Saved search: All Kubernetes Logs — columns k8s_namespace, k8s_pod, k8s_container, log_level, message. Sorted newest first.
7
Saved search: Error Logs — same columns minus log_level, bound to the k8s-error-* data view.
Self-healing: ttlSecondsAfterFinished
The Job has ttlSecondsAfterFinished: 30. Kubernetes deletes it 30 seconds after it completes. On the next ArgoCD sync, ArgoCD sees the Job is missing and recreates it, which re-runs the script. All operations are idempotent (saved objects use ?overwrite=true), so re-running is always safe.

5. Index Strategy

Index pattern Example index name Contains Kibana data view
k8s-logs-{ns}-YYYY.MM.dd k8s-logs-argocd-2026.07.25 All logs from namespace argocd k8s-logs-* (default)
k8s-error-YYYY.MM.dd k8s-error-2026.07.25 error / fatal / critical level logs from all namespaces k8s-error-*
k8s-misc-YYYY.MM.dd k8s-misc-2026.07.25 Logs without a Kubernetes namespace (non-k8s sources) k8s-misc-*

Index template: k8s-single-node (priority 200)

PUT /_index_template/k8s-single-node
{
  "index_patterns": ["k8s-*"],
  "priority": 200,
  "template": {
    "settings": { "number_of_replicas": 0 }
  }
}

This template is registered by the ES sidecar on every pod start. Priority 200 beats:

  • logs built-in template — priority 100 (would force data-stream mode)
  • Logstash-managed templates — priority 1

Result: all k8s-* indices are plain date-based indices with replicas=0 → always green on a single-node cluster.

7. Full Startup Sequence (first deploy)

1
ArgoCD detects a new commit → applies all manifests to the observability namespace.
2
ESO reads vault-secretstore and creates the elasticsearch-credentials K8s Secret with the password from Vault.
3
Elasticsearch StatefulSet starts. On first start it sets up its data directory, creates the elastic user with the provided password, and disables TLS.
4
The password-sync sidecar detects ES is healthy → syncs the password → registers the k8s-single-node index template → sleeps.
5
Filebeat DaemonSet starts on the node. It begins harvesting /var/log/containers/*.log, enriches each event with Kubernetes metadata, and streams to Logstash:5044.
6
Logstash Deployment starts, loads its pipeline, and begins receiving Beats events. The filter stage enriches them; the output stage writes to k8s-logs-{namespace}-YYYY.MM.dd indices.
7
create-kibana-token Job: waits for credentials secret → waits for ES security API → calls manage-es-token.js create → stores the service account token in the kibana-es-serviceaccount-token secret.
8
Kibana Deployment starts. It reads the token secret and connects to ES immediately — no interactive login or token copy needed.
9
kibana-setup Job: waits for Kibana /api/status to return "level":"available" → deletes any stale data views → creates k8s-logs-* / k8s-error-* / k8s-misc-* data views, dashboard, and saved searches.
10
After 30 s the setup Job self-deletes. Kibana is fully usable at http://<node-ip>:30201.

8. Problems Encountered & How They Were Solved

ProblemRoot CauseFix
Filebeat not collecting logs Only /var/log/containers was mounted; the symlink chain requires /var/log/pods and /var/lib/docker/containers too. Also missing NODE_NAME env var for k8s metadata processor. Added both missing volume mounts and the NODE_NAME env var via fieldRef: spec.nodeName.
Logstash HTTP 400 writing to ES ES 9 built-in logs index template (priority 100) intercepts logs-*-* patterns and forces data-stream semantics. Data streams reject plain index write operations. Renamed all output indices from logs-k8s-* / logs-error-* / logs-misc-* to k8s-logs-* / k8s-error-* / k8s-misc-*.
All indices yellow ES defaults to number_of_replicas: 1 but there is only one node — the replica shard can never be placed. Added k8s-single-node index template (priority 200, replicas=0) registered by the sidecar. Also patches existing indices via PUT /k8s-*/_settings.
Kibana needs manual token creation ES service account tokens are not stored anywhere accessible — they must be generated via the ES API and injected as a K8s secret. Automated via create-kibana-token Job + manage-es-token.js Node.js script. Fully idempotent: deletes old token, creates new one, writes to K8s secret.
Kibana data views showed no fields The setup Job had completed with the old index names (logs-k8s-*). After the rename it stayed Completed forever — ArgoCD never re-ran it. Added ttlSecondsAfterFinished: 30 so the Job self-deletes and is recreated on the next sync. Added a delete step in setup.sh to remove stale data views before creating correct ones.
Password drift after PVC restore ES stores its own hashed password in the data directory. After restoring from a PVC snapshot the stored hash may not match the current secret. The password-sync sidecar forces a password reset via PUT /_security/user/elastic/_password on every pod start.
TLS errors on fresh cluster ES 9 auto-generates self-signed certificates and enables TLS on first boot when no config overrides are set. Set xpack.security.http.ssl.enabled: false and xpack.security.transport.ssl.enabled: false via env vars on the StatefulSet.

Watch Logstash pipeline

kubectl logs -n observability -l app=logstash --tail=50 -f

Watch ES sidecar (password sync + index template)

Check index health in ES

kubectl exec -n observability elasticsearch-0 -- \
  curl -s -u "elastic:$(kubectl get secret elasticsearch-credentials \
    -n observability -o jsonpath='{.data.password}' | base64 -d)" \
  "http://localhost:9200/_cat/indices/k8s-*?v&h=health,status,index,docs.count,store.size"

kubectl logs -n observability job/create-kibana-token -c create-token

kubectl delete job kibana-setup -n observability --ignore-not-found
argocd app sync <app-name>

kubectl logs -n observability job/kibana-setup -c setup

10. What You See in Kibana

After full startup, open http://<node-ip>:30201. You will find:

  • Stack Management → Data Views: k8s-logs-* (default), k8s-error-*, k8s-misc-* — each with all enriched fields indexed.
  • Discover: live stream of all container logs, searchable by k8s_namespace, k8s_pod, k8s_container, log_level, message.
  • Dashboard → Kubernetes Logs Overview: histogram of log events split by namespace.
  • Discover → Saved Searches: "All Kubernetes Logs" and "Error Logs".
